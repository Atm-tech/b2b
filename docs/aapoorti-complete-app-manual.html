1. Application summary

Aapoorti B2B is an internal procurement, sales, inventory, payment, warehouse and delivery operating system. A single shared snapshot supplies the frontend with role-filtered users, masters and operational records. Users enter purchase and sales carts, upload proofs, receive goods, reserve and dispatch stock, reconcile payments and track every order through status, ledger and notes.

2. Complete business flow: top to bottom

  1. Administrator setup: create users, assign one or more roles and warehouses, create warehouses/yards, maintain products and configure payment/delivery settings.
  2. Party setup: Accounts/Purchaser/Sales create suppliers and shops with GST, banking, contact and location details.
  3. Purchase booking: Purchaser selects supplier, warehouse and products; enters quantity, rate, GST/tax mode, delivery/payment mode, optional advance and note; submits a grouped purchase cart.
  4. Supplier payment: Purchaser or Accounts records payments/proof; Accounts verifies, rejects, disputes or resolves them. Accounts can record supplier advance payments before an order exists.
  5. Inbound movement: Dealer delivery is tracked to the warehouse, or Delivery Manager assigns self-collection. Payment delivery can be part of the delivery task.
  6. Warehouse receipt: Warehouse Manager records received quantity and actual/container/net weight, uploads weighing proof, confirms partial receipt and flags tolerance exceptions.
  7. Inventory creation: accepted receipt quantity becomes a traceable inventory lot. Available, reserved and blocked quantities feed the stock view.
  8. Sales booking: Sales chooses a shop, searches the catalogue, adds cart lines, applies rate/CD/TOD/GST rules, chooses warehouse, payment and delivery; stock shortages can create probationary sales records rather than disappearing silently.
  9. Sales collection: Sales records collected amounts; Collection Agent follows assigned outstanding orders; Accounts reconciles submitted payments.
  10. Warehouse dispatch: Warehouse creates delivery dockets, records weights/proofs and marks orders ready. Delivery Manager may group dockets into consignments and assign internal/external transport.
  11. Last mile: delivery user accepts the task, reaches pickup, marks picked/handed over/delivered, handles route stops, cash collection/handover and proof uploads.
  12. Closure: delivery is complete, payment is verified/reconciled, stock has moved, ledger pending amount is zero, and exceptions/notes are resolved. Returns use dedicated purchase-return or sales-return trails.

3. Login, navigation and shared interface

Login and session

  • Login requires username and password at POST /auth/login.
  • The API returns the user, a random session token and the initial filtered application snapshot.
  • The browser stores user, token, last active view, simple-mode choice, sidebar state, delivery-manager warehouse selection and in-progress workspace drafts in localStorage.
  • Every protected API request sends Authorization: Bearer <token>.
  • Logout deletes the server session and clears the stored browser session/navigation values.
Security note: the current source stores passwords in plain text and compares them case-insensitively. Seed credentials are also present in source. Before public or high-risk use, replace this with salted password hashing, password reset/rotation, session expiry, rate limiting and audit logging. Change all seeded passwords immediately.

5. Screen-by-screen element catalogue

Home / Overview

Elements: role-specific greeting and navigation cards; business metrics; pending badges; QR scanner launcher; recent or pending work; shortcuts to payments/orders/stock/delivery; Accounts purchase-advance entry; daily sales report PDF action where available.

Use: start each shift here, open the largest pending queue, and return after completing a task to verify the count reduced.

Users (Admin)

Create fields: Username, Name, Mobile, Roles (multi-select), Warehouses (multi-select), Password. Default password in the form and API is 1234 when not changed.

Directory columns: Username, Name, Roles, Warehouses, Mobile. A blank warehouse list means broad/all-warehouse visibility in current mapping.

Action: Create user. There is no user edit/deactivate endpoint in the current UI/API.

Warehouses (Admin)

Create fields: Code/ID, Name, City (initially Bhopal), Type (Warehouse or Yard), Address.

List columns: Code, Name, City, Type. Warehouse codes are referenced by products, orders, inventory, receipts, dockets, consignments and scoped users, so create carefully.

Products (Admin)

Core fields: SKU, Name, Division, Department, Section, Category, Sub-category, Unit, default GST rate (NA/0/5/12/18/40), tax mode (NA/Exclusive/Inclusive), default weight kg, tolerance kg, tolerance %, allowed warehouses, quantity slabs, RSP and MRP.

Extended import fields supported by the record/importer: remarks, category 6, site name, barcode, supplier name, HSN code, article name, item name, brand, short name and size.

Actions: create, edit, delete; paste/import bulk rows; upload CSV/XLS/XLSX; download/use template where exposed; search/filter product directory. During startup the backend infers missing weights from product text such as grams, kilograms, litres, millilitres, additive/free packs and multipacks.

Operational rule: allowed warehouses, weight and tolerance directly affect whether a product can be received and how receipt variance is flagged. GST defaults feed purchase and sales lines.

Parties

Types: Supplier and Shop.

Fields: Type, Name, GST Number, Bank Name, Bank Account Number, IFSC Code, Mobile Number, Address, City, Contact Person; record model also supports delivery address/city, latitude, longitude and location label.

Actions: create, edit, filter by supplier/shop, review vitals and use a party in purchase, sales, payment and delivery workflows. Current create/update API requires the main identity, GST, banking, contact and address fields.

Purchase: new grouped PO

Header fields: supplier, receiving warehouse, delivery mode (Dealer Delivery/Self Collection), payment mode, cash timing when applicable, operation date, order note, optional location and optional advance payment.

Line/catalog fields: product/SKU search, quantity, rate, taxable amount, GST rate, GST amount, tax mode and previous-rate context. Cart mode allows multiple products under one public cart/order group.

Automatic calculations/effects: expected weight = product default weight × ordered quantity; tax totals are normalized; initial status represents an order placed pending delivery; a purchase ledger entry is created/updated; advance payment can be recorded; a PO/group ID is generated.

Actions: add/remove cart items, submit order, reopen/update an eligible group from Purchases, print/download/share invoice or estimate, view/download QR/status.

Purchases: grouped order summary

Elements: grouped PO/cart rows, supplier, items, quantity/value, delivery status, payment status, outstanding amount, created date, search/filter, pending badges and analytics variants for Accounts/Data Analyst/Admin.

Actions by permission: Purchaser opens an order for update; authorized users view status QR, PDF/invoice and WhatsApp/share output; Accounts reviews payment position; analysts use summaries without editing the operational order.

Purchase Return

Fields: mode (Adhoc/Planned), optional linked purchase group and line, supplier, warehouse, product, quantity, rate, reason, note and optional photo/proof.

Reasons: Rate Difference, Damage, Quality Issue, Wrong Item, Excess Quantity, Other. Multiple lines share a generated return-group ID. Only Purchaser creates purchase returns.

Sales: customer and catalogue cart

Customer step: choose existing shop or open the party-creation path. Shop selection carries GST/contact/delivery context.

Catalogue elements: text search, category/brand/product browsing, optional speech recognition, product cards, rate pop-up, quantity, available stock, warehouse, add-to-cart and cart badge/drawer.

Checkout fields: shop, warehouse, line quantities and rates, CD/TOD rate and discounts, taxable amount, GST rate/amount/tax mode, payment mode/cash timing, collected or advance amount, delivery mode (Self Collection/Delivery), delivery charge, operation date and note.

Actions: new sale, customer select, search/add/remove/change cart lines, summary, payment step, finalize, continue shopping, create invoice/estimate, download/print/share PDF, QR status, and later reopen via Sales Orders when permitted.

Automatic effects: stock is reserved/allocated where available; delivery charge applies once per grouped delivery order; status begins Booked or Self Pickup; ledger entry is created; an advance payment may be created; insufficient stock can produce a probationary-sales record with pending quantity for later clearing.

Sales Orders / Sales summary

Elements: grouped order/customer rows, line and amount totals, fulfilment status, payment state, outstanding collection, collection assignment and notes. Role-specific analyst and collection views are used.

Actions: update eligible order, record collection/payment, assign collection agent through an operational note, log override note, open QR status, invoice print/download/share. Warehouse dispatch actions update readiness and docket state through the warehouse operations views.

Sales Return

Fields: mode, optional linked sales group/line, shop, warehouse, product, quantity, rate, reason, note and photo/proof.

Effect: records a grouped return audit trail and can create inventory with source type Sales Return. Only Sales creates sales returns.

Payments

The screen changes by role.

  • Purchaser: supplier payment entries connected to purchase orders, amount/mode/cash timing/reference/voucher/UTR/proof/status/note/date.
  • Sales: customer collection capture connected to sales groups; proof upload and submitted/pending state.
  • Collection Agent: assigned outstanding orders, collection amount/reference/proof and collection follow-up.
  • Accounts: unified purchase/sales review, create supplier advance, edit payment, verify/reject/dispute/resolve, inspect proof and reconcile ledger.

Payment modes: Cash, Card, UPI, NEFT, RTGS and Cheque, subject to Admin settings. Cash timing values are In Hand, At Delivery and Later.

Verification states: Pending, Submitted, Verified, Rejected, Disputed, Resolved. Verified/settled amounts reduce the linked ledger pending balance; collection status supports None, Assigned, Collected and Reconciled.

Proof: JPEG, PNG, WebP or PDF; default maximum 8 MiB. Proof URL remains /uploads/payment-proofs/<filename>.

Receipts (Warehouse Manager)

Fields: purchase order, warehouse, received quantity, actual/gross weight, container weight, computed net weight, weighing proof, cash proof when relevant, note, operation date and explicit partial confirmation.

Generated values: GRC number, receiver identity, ordered/pending quantity, expected weight, variance kg, partial flag and exception flag.

Actions: receive, upload proof, confirm partial, flag/unflag/update note. Accepted quantity updates the PO and inventory. Weight variance is tested against product tolerance in kg/percent.

Stock

Summary fields: warehouse/code/name, SKU/product, available, reserved and blocked quantities. Analyst/Admin/Accounts variants provide aggregated views; Warehouse Manager sees operational stock.

Sources: accepted purchase receipts and sales returns. Sales reservations reduce usable availability; exceptions may stay blocked. Probationary sales separately identify quantities sold before stock was available.

Ledger

Fields: ledger ID, side (Purchase/Sales), linked order/group, party, goods value, paid amount, pending amount and status (Pending/Partial/Settled).

Working: the ledger is an operational reconciliation view derived/maintained from orders and payments. It is not a full double-entry accounting general ledger. Accounts has richer filters/workspaces; other permitted roles receive scoped visibility.

Delivery Manager: Home, Inbound and Dispatch

Home: pending counts, warehouse selector and navigation to inbound or dispatch queues.

Inbound fields/actions: purchase-side linked order IDs, dealer/self-collection mode, internal/external transport, from/to, assignee, pickup/drop times, route hint/stops, vehicle, freight, payment action, cash requirement, status, proofs and date.

Dispatch fields/actions: select ready sales dockets/orders, create or update tasks, assign delivery user(s), group/merge compatible delivery tasks, create consignments, set warehouse, internal/external transport, vehicle/freight and route stops.

Task states: Planned → Picked → Handed Over → Delivered. Delivery dockets and consignments have their own readiness/pickup/delivery states.

Current Delivery / New Assignment

Elements: role/user-filtered assignments, order and route stops, supplier/shop and warehouse locations, product summary, amount/payment requirement, acceptance/action buttons, proof uploads and last-action time.

Typical execution: open New Assignment → accept/mark Picked → reach supplier or warehouse → check/pick items → record payment delivered/collected when required → upload weight/cash/delivery proof → Handed Over → Delivered. In Delivery focuses purchase/inbound tasks; Out Delivery/Delivery focuses sales/outbound tasks.

Delivery dockets and consignments

Docket fields: docket ID, sales order, shop, SKU, warehouse, quantity, gross/container weight, proof, optional consignment and status (Pending Packing, Ready, Tagged, Pending Pickup, Out for Delivery, Delivered).

Consignment fields: ID, docket IDs, warehouse, assigned person, total weight, status (Draft, Ready, Pending Pickup, Out for Delivery, Delivered), creator/date.

Goods Warrants (Accounts)

Fields: outlet (Awadhpuri, Koh E Fiza, New Market, Kolar, Indrapuri), issued to, issuer name, received amount, warrant amount/denomination, Cash/Cheque, cheque number, cash collected date, issue date/start, valid-through date and note.

Actions: create one, bulk-create denominations with monthly limits, edit, clear list, render/print warrant document and use the configured logo endpoint. Warrant number is unique.

Excel Maker (Accounts)

A standalone utility converts pasted/structured text into a downloadable Excel workbook. It is client-side and uses the XLSX library; use it for ad-hoc tabular output, not as a replacement for database backup.

Settings (Admin)

Payment method rows: code, label, Active checkbox and Allows Cash Timing checkbox.

Delivery charge: model (Fixed/Per Km) and numeric amount. Current sales calculation applies the configured amount to delivery orders; the grouped order carries it once.

Defaults on a new database: Cash/Card/UPI/NEFT/RTGS active, Cheque inactive; Cash allows cash timing; fixed delivery amount 350.

Notes

Fields: Entity Type, Entity ID, Visibility, Note. Entity types: Purchase Order, Receipt, Sales Order, Payment, Delivery, Inventory, Party. Visibility: Restricted, Operational, Management.

List: entity, ID, note, author and visibility. Notes are the human-readable audit/exception trail; current enforcement primarily filters snapshot data/roles rather than implementing a complete record-by-record confidentiality policy.

Calculations

  • Expected receipt weight: default product weight kg × ordered/expected quantity.
  • Net receipt weight: actual/gross weight − container weight.
  • Weight variance: net weight − expected weight; compared with tolerance kg and tolerance percent to set flagged status.
  • Exclusive tax: taxable base plus calculated GST. Inclusive tax: tax is separated from the entered inclusive value. NA: non-GST estimate behavior.
  • Sales line value: quantity/rate with CD/TOD adjustments, taxable value and GST, plus applicable grouped delivery charge.
  • Ledger: pending = goods value − accepted paid amount; status becomes Pending, Partial or Settled.
  • Stock: usable stock is aggregated from inventory lots after available/reserved/blocked movements. Returns and probationary clearing modify the trail.

11. Install, run, build and deploy

Local prerequisites

  • Node.js and npm
  • PostgreSQL 16 or Docker Desktop/Compose
  • A modern browser; camera/image QR decoding varies by browser

Local run

npm install
npm run postgres:up
npm run dev

Frontend normally runs at http://localhost:5173; API at http://localhost:8080. Verify GET /health returns ok: true and the expected proof-storage mode.

Render

render.yaml defines an API web service, static frontend, persistent upload disk and PostgreSQL database. Configure production database, exact frontend origin and R2 secrets in the dashboard. Health path is /health. The static frontend rewrites all routes to /index.html.

Vercel frontend

The root vercel.json installs the domain/web workspaces, builds the domain then web, and publishes apps/web/dist. Set VITE_API_BASE_URL to the deployed Render API before building.

Cloudflare R2

  1. Create a private bucket, normally aapoorti-proofs.
  2. Create a bucket-scoped Object Read & Write token.
  3. Set all R2 credentials and redeploy.
  4. Confirm /health reports cloudflare-r2.
  5. Test one upload/open operation for each proof category before removing any persistent disk.
Do not enable a public r2.dev URL for private business proofs. The current API proof GET is itself unauthenticated, so production hardening should add authorization or signed short-lived URLs.

12. Daily controls, backup and troubleshooting

Start-of-day checklist

  1. Confirm API health and database connectivity.
  2. Open Home for each operating role and review pending badges.
  3. Accounts reviews submitted/disputed payments and advances.
  4. Warehouse reviews receipt and dispatch queues.
  5. Delivery Manager checks unassigned/late inbound and outbound work.
  6. Sales/Purchaser check open order and exception groups.

End-of-day checklist

  1. All physical receipts have a GRC, quantities, weights and required proof.
  2. All completed delivery actions have correct status, route stops, proof and cash handover.
  3. Accounts matches collections/supplier payments and investigates rejected/disputed items.
  4. Review stock negative/probationary/blocked conditions and ledger pending balances.
  5. Record unresolved exceptions in Notes with the correct entity ID.
  6. Run/confirm database and proof-storage backups.

Backup and recovery

  • Back up PostgreSQL with a managed snapshot and/or pg_dump. Test restore to a separate database.
  • Back up the local uploads directory if local storage is active. For R2, enable retention/versioning appropriate to policy.
  • Database and proofs must be backed up together; the database stores proof filenames, not the file bytes.
  • Before reset/cleanup/delete-all endpoints or utilities, take and verify a backup.

Known hardening priorities

  1. Hash passwords with Argon2/bcrypt; remove/rotate seed passwords and add reset policy.
  2. Add session expiry/revocation details, login throttling and CSRF strategy as appropriate.
  3. Protect proof downloads with record authorization or signed expiring URLs.
  4. Add formal database foreign keys/check constraints where compatible with migration history.
  5. Add a complete immutable audit log for edits, deletes, verification and status transitions.
  6. Split the very large frontend component into tested modules; add automated API/unit/end-to-end tests and CI gates.
  7. Remove the hard-coded Windows goods-warrant logo path and configure it through an environment variable or bundled asset.
  8. Document and gate destructive reset/clear endpoints with confirmation, backup and finer permissions.

13. Definition of a completed order cycle

A purchase-to-sale cycle is complete only when: masters are correct; PO/SO groups and quantities match the physical transaction; inbound receipt and stock movement are posted; outbound docket/task is delivered or self-pickup is closed; payment proof is verified/reconciled; ledger pending is zero; returns, shortages, weight flags, cash handover and operational notes have no unresolved exception.

Clean-machine installation procedure

  1. Install an approved Node.js LTS release, npm, PostgreSQL 16 and Git. Record exact versions used for acceptance.
  2. Clone or extract the identified release into a new directory. Do not copy the vendor’s node_modules.
  3. Copy .env.example to a local untracked .env and set client-owned values.
  4. Create an empty PostgreSQL database and restricted application user, or start the Docker Compose database for local evaluation.
  5. Run npm ci when the lockfile is authoritative; use npm install only when intentionally updating the lockfile.
  6. Run npm run build. Treat TypeScript/build failures as a failed release.
  7. Start API and frontend, open /health, log in with a newly rotated Admin account, and run the smoke test below.
  8. Disable/change seed credentials before exposing the service beyond an isolated acceptance network.

Minimum smoke test

  1. Health endpoint reports OK and correct proof-storage mode.
  2. Admin login/logout and role-based navigation work.
  3. Create test warehouse, product, supplier, shop and non-production role users.
  4. Create grouped PO, purchase payment and inbound task; receive it and confirm stock.
  5. Create sales cart, payment, docket, consignment/task and deliver it.
  6. Confirm ledger settlement, invoice PDF, Excel export and QR/status view.
  7. Upload/open one proof in every category.
  8. Create one purchase return and one sales return.
  9. Verify each role sees only expected screens and scoped records.
  10. Back up, restore into a separate database/storage location and repeat login/read checks.

Release process

  1. Freeze and identify the source commit; update version, changelog and this manual.
  2. Review dependency/security advisories and decide documented remediations.
  3. Build and test in a clean environment, not only the developer workstation.
  4. Take production database/proof backups and verify recovery points.
  5. Deploy database-compatible API first where required, then frontend; monitor health and logs.
  6. Run smoke tests and reconcile record counts. Keep a defined rollback artifact and decision window.
  7. Record release time, operator, commit, environment changes and acceptance result.

Rollback

Application rollback means redeploying the previously accepted source/build with compatible configuration. Database rollback is not the same operation: do not reverse schema/data changes by copying old files. Use reviewed forward fixes or restore a verified database/proof backup only after the business owner accepts loss of transactions since that recovery point.
